# ONNX 변환 전후 비교

fine-tuning한 비꼼 탐지 모델을 ONNX로 변환하기 **전**(PyTorch)과 **후**(ONNX Runtime)의 성능을 같은 데이터, 같은 조건으로 비교한다. 이 결과는 이후 pruning·양자화 결과를 비교할 **기준(baseline)**이 된다.

## 요약 (PC, test 셋, 스레드 4개)

| 항목 | 변환 전 (PyTorch) | 변환 후 (ONNX) | 변화 |
|---|---|---|---|
| BA / M-F1 (%) | 72.8 / 72.5 | 72.8 / 72.5 | **변화 없음** |
| 예측 일치율 | | | **100%** (1,037개 모두 같음) |
| 지연시간 평균 (ms, batch 1) | 118.9 | 78.4 | **34% 감소 (1.52배 빠름)** |
| 모델 로드 시간 (초) | 2.65 | 1.02 | **62% 감소** |
| 프로세스 최대 메모리 (MB) | 1,170 | 1,063 | 9% 감소 |
| 파일 크기 (MB) | 422.0 | 422.2 | 같음 |

- **정확도 손실이 전혀 없다.** 모든 지표가 소수점까지 같고, 예측도 100% 일치한다.
- **속도는 약 1.5배 빨라졌다.** 모델 로드 시간도 절반 이하로 줄었다.
- **파일 크기는 그대로다.** 변환은 형식만 바꾸는 작업이라 크기는 pruning·양자화 단계에서 줄여야 한다.

## ONNX 변환이란

PyTorch 모델 파일(`model.safetensors`)에는 가중치 숫자만 들어 있다. 이 숫자로 어떤 계산을 하는지는 Python 코드(PyTorch, transformers)에 있어서, 실행하려면 Python 환경 전체가 필요하다.

ONNX 파일(`model.onnx`)에는 가중치와 함께 **계산 순서(연산 그래프)**가 들어 있다. 그래서 ONNX Runtime만 있으면 Python 없이 Android·iOS 앱이나 C++에서 돌릴 수 있다. 계산 순서를 미리 알기 때문에 연산을 합치는 등의 최적화도 할 수 있다.

변환 방법은 [PROJECT.md](PROJECT.md#2단계-onnx-변환-및-기준-성능)와 [export_onnx.py](../scripts/export_onnx.py)를 참고한다.

## 실험 설정

| 항목 | 값 |
|---|---|
| 변환 전 | PyTorch 2.6.0, transformers 5.22.1 (`model/model.safetensors`) |
| 변환 후 | ONNX Runtime 1.31.1, CPUExecutionProvider, 그래프 최적화 ORT_ENABLE_ALL (`onnx/model.onnx`, opset 17, fp32) |
| 장치 | PC (Windows 10, CPU 12 논리 코어), Python 3.13.5 |
| 데이터 | KoCoSa test 1,037개, validation 1,321개 |
| 입력 | `context` + `response` 문장쌍, 최대 256 토큰 (학습 때와 같은 방식) |
| 스크립트 | [benchmark.py](../scripts/benchmark.py) |

**측정 방법**
- 두 모델은 각각 별도 프로세스에서 실행해서 메모리 측정이 섞이지 않게 했다. 두 측정 사이에 10초를 쉬었다.
- **지연시간:** 문장쌍 1개(batch 1)를 넣고 결과가 나올 때까지의 시간. 토크나이저 시간은 뺐다. 데이터 앞쪽 32개(평균 약 103 토큰, 최대 155~173 토큰)를 돌아가며 50번 재고, 그 전에 5번 예열했다.
- **정확도 평가:** 데이터 전체를 batch 8로 추론했다.
- **메모리:** 모델을 불러오면서 늘어난 메모리와, 측정 중 프로세스가 쓴 최대 메모리.

## 결과

### 1. 정확도 — 변화 없음

**Test 셋 (1,037개)** — 논문 Table 8 형식, 단위 %

| Model | BA | M-F1 | W-F1 | Precision-S | Recall-S | Precision-N | Recall-N | Acc | F1(S) |
|---|---|---|---|---|---|---|---|---|---|
| 변환 전 (PyTorch) | 72.8 | 72.5 | 73.4 | 69.8 | 96.3 | 91.6 | 49.3 | 75.1 | 81.0 |
| 변환 후 (ONNX) | 72.8 | 72.5 | 73.4 | 69.8 | 96.3 | 91.6 | 49.3 | 75.1 | 81.0 |

**Validation 셋 (1,321개)**

| Model | BA | M-F1 | W-F1 | Precision-S | Recall-S | Precision-N | Recall-N | Acc | F1(S) |
|---|---|---|---|---|---|---|---|---|---|
| 변환 전 (PyTorch) | 70.6 | 71.3 | 73.7 | 73.0 | 95.4 | 86.5 | 45.8 | 75.9 | 82.7 |
| 변환 후 (ONNX) | 70.6 | 71.3 | 73.7 | 73.0 | 95.4 | 86.5 | 45.8 | 75.9 | 82.7 |

**두 모델 출력 비교**

| 분할 | 예측 일치율 | 출력값(logit) 최대 차이 |
|---|---|---|
| test | 100% (1,037 / 1,037) | 1.8 × 10⁻⁵ |
| validation | 100% (1,321 / 1,321) | 4.4 × 10⁻⁶ |

출력값 차이는 소수점 다섯째 자리 이하다. 계산 순서가 조금 달라서 생기는 부동소수점 오차 수준이고, 예측 결과를 바꿀 만큼 크지 않다.

### 2. 속도

**지연시간 (batch 1, 단위 ms)**

| 스레드 | 모델 | 평균 | 중앙값 | p90 | 최소 | 최대 |
|---|---|---|---|---|---|---|
| 4 | 변환 전 (PyTorch) | 118.9 | 113.6 | 154.8 | 79.5 | 193.1 |
| 4 | **변환 후 (ONNX)** | **78.4** | **74.1** | **104.4** | 45.7 | 116.5 |
| 1 | 변환 전 (PyTorch) | 235.8 | 223.9 | 303.4 | 111.5 | 368.5 |
| 1 | **변환 후 (ONNX)** | **188.8** | **180.9** | **245.3** | 75.9 | 334.7 |

스레드 4는 test 셋, 스레드 1은 validation 셋 앞쪽 32개로 측정했다(입력 길이 분포는 거의 같다: 평균 103 토큰).

| 스레드 | 평균 지연시간 감소 | 속도 배수 |
|---|---|---|
| 4 | 34% | 1.52배 |
| 1 | 20% | 1.25배 |

- 스레드가 많을수록 ONNX의 이점이 커진다. ONNX Runtime이 여러 코어에 작업을 더 효율적으로 나누기 때문으로 보인다.
- 모바일은 보통 고성능 코어가 4개 안팎이라, 실제 폰에서는 스레드 1~4 사이 결과에 가까울 것으로 예상된다. 정확한 값은 Android 측정으로 확인한다.

**처리량과 로드 시간 (스레드 4)**

| 항목 | 변환 전 (PyTorch) | 변환 후 (ONNX) | 변화 |
|---|---|---|---|
| 평가 처리량 (개/초, batch 8, test) | 8.18 | 10.59 | +29% |
| 모델 로드 시간 (초) | 2.65 | 1.02 | −62% |

### 3. 메모리와 크기

| 항목 | 변환 전 (PyTorch) | 변환 후 (ONNX) | 변화 |
|---|---|---|---|
| 파일 크기 (MB) | 422.0 | 422.2 | 같음 |
| 모델 로드로 늘어난 메모리 (MB) | 537 | 449 | −16% |
| 프로세스 최대 메모리 (MB) | 1,170 | 1,063 | −9% |

- 프로세스 최대 메모리에는 Python, 라이브러리, 데이터셋이 차지하는 부분도 들어 있다. 모델 자체의 차이는 "로드로 늘어난 메모리"(약 90MB 감소)로 보는 것이 정확하다.
- 이 측정은 Python으로 실행한 값이다. Android 앱처럼 Python 없이 ONNX Runtime만 쓰면 메모리는 훨씬 적게 든다.

## 해석

1. **ONNX 변환은 정확도 손실 없이 속도를 높였다.** 변환 후에도 모델의 판단이 하나도 바뀌지 않았으므로, 이후 단계에서 ONNX 모델을 기준으로 삼아도 된다.
2. **크기는 줄지 않았다.** 422MB는 모바일 앱에 넣기에 크다. 다음 단계인 pruning(불필요한 가중치 제거)과 양자화(fp32 → int8 등)로 줄여야 한다. int8 양자화만으로도 약 1/4(약 110MB)이 될 것으로 예상한다.
3. **pruning·양자화 결과는 이 표와 같은 형식으로 비교한다.** 특히 BA·M-F1이 얼마나 떨어지는지와 예측 일치율을 함께 본다.

## 측정의 한계

- **같은 PC에서도 실행할 때마다 절대 시간이 달라진다.** 같은 조건(validation, 스레드 4)으로 앞서 측정했을 때는 PyTorch 98.1ms, ONNX 69.7ms(29% 감소)였다([20261110_132109_pc.json](../results/benchmark/20261110_132109_pc.json)). 백그라운드 작업 등에 따라 절대값은 20% 안팎으로 달라지지만, ONNX가 약 30% 빠르다는 상대 비교는 일관됐다.
- 지연시간은 32개 문장의 평균이다. 입력 길이(토큰 수)가 길어지면 지연시간도 늘어난다.
- PC 결과다. 모바일 결과는 [MOBILE_BENCHMARK.md](MOBILE_BENCHMARK.md)의 방법으로 측정한 뒤 추가한다.
